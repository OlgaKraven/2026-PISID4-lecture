## Field Service: учебный контекст

Инженер работает офлайн, фиксирует диагностику, работы, запчасти, фотографии, геолокацию и подпись клиента.

Отсутствие сети меняет путь подтверждения. Инженер должен сохранить работу на устройстве и понимать, что отправка ещё не завершена. Позже состояние сервера может потребовать согласования. Числа и идентификаторы далее относятся к учебным данным.

Цель сценария — рабочий результат, который участник должен получить при выполнении последовательности действий.

## Предусловие

Предусловие — состояние данных, полномочий и окружения, которое должно выполняться до начала сценария.

Предусловия помогают понять, можно ли начать работу, но не гарантируют их сохранение до конца. Назначение инженера может измениться во время отсутствия сети. Поэтому предварительная проверка улучшает интерфейс, а сервер перед применением операции заново проверяет актуальные условия. При конфликте нужен путь сохранения результата без ложного сообщения об успехе.

## Полный разбор решения

Учебная синхронизация визита 81 отправляет подпись после офлайн-работы. Сервер сообщает, что назначение инженера изменилось.

Права и состояние проверяются в момент серверной операции, а не только при загрузке формы. Для «До офлайна» сопоставлены устройство eng-01: Визит 81 назначен ENG-01; сервер: Назначение ENG-01. Для «Пока нет связи» сопоставлены устройство eng-01: Черновик закрытия сохранён; сервер: Назначение изменено диспетчером. Для «Повторная отправка» сопоставлены устройство eng-01: Передан старый локальный результат; сервер: Конфликт; закрытие не выполнено.

Шаг 1. Сопоставить снимки. Локальный контекст и серверное назначение различаются. Расхождение — ожидаемый случай распределённого взаимодействия, а не потеря формы.

Шаг 2. Отправить закрытие. Сервер обнаруживает смену назначения. Офлайн-предусловие не переносится автоматически на момент синхронизации.

Шаг 3. Показать отказ. На экране конфликт, локальные данные остаются. Приложение не рисует успешное завершение вместо отказа.

Шаг 4. Передать разработчику. Описаны сообщение, сохранность и путь согласования. Одного макета успешного состояния недостаточно для реализации этого поведения.

## Конфликт назначения

Теперь самостоятельный случай «Конфликт назначения» с другими данными. Нажмите «Разбор задачи». E3 отправляет локальное закрытие V44. До синхронизации диспетчер переназначил визит E8. Правило: закрывать может только текущий назначенный инженер; при отказе локальный результат сохраняется. Выберите состояние conflict или completed и действие keep или clear для черновика.

Сначала запишите прогноз. Выполните первый шаг, введите результат и нажмите его проверку. Второй шаг откроется после верного первого. Пауза для самостоятельной работы и обоснования. После попытки можно открыть разбор отдельной кнопкой; до этой команды решение не показывается. Завершите сравнением изменённого условия и вернитесь кнопкой «Вернуться к слайду».

Вопросы для обсуждения: Почему каждый результат следует из данных? Что изменится в сравнительном условии и что сохранится?

Разбор после самостоятельной попытки. Исходная таблица: Участник | Назначение V44.
Автор запроса | E3
Текущее назначение на сервере | E8

Шаг 1. Сравните отправителя с актуальным назначением на сервере. Определите результат проверки.
В поле «Состояние ответа» введите conflict. Нажмите «Проверить шаг 1». На экране: «Первый результат проверен. Теперь отдельно выполните второй шаг.». В таблице результата появится это значение со статусом «Проверено».
Почему: E3 не совпадает с текущим назначением E8. По заданной политике закрытие не разрешено и completed не возникает.
При расхождении поле показывает инструкцию и требуемый формат: conflict — конфликт; completed — подтверждённое завершение. Исправьте значение и повторите проверку.

Шаг 2. Примените заданное правило сохранности при отказе.
В поле «Действие с черновиком» введите keep. Нажмите «Проверить шаг 2». На экране: «Оба результата проверены. Сопоставьте их с исходными данными и обоснуйте вывод.». В таблице результата появится это значение со статусом «Проверено».
Почему: Введённый результат сохраняют для согласования; конфликт назначения не является командой очистить черновик.
При расхождении поле показывает инструкцию и требуемый формат: keep — сохранить; clear — очистить. Исправьте значение и повторите проверку.

После попытки нажмите «Показать разбор после попытки». Сервер видит E8, а запрос пришёл от E3, поэтому возвращается конфликт и данные остаются для согласования.
Изменённое условие: Если на момент проверки V44 всё ещё назначен E3. Проверка назначения пройдёт. Для completed дополнительно должны пройти остальные проверки закрытия.
Граница: Кто согласует результат и разрешит конфликт, определяется отдельным процессом; его здесь не угадывают.
Изменение второго ответа скрывает разбор. Изменение первого дополнительно очищает второй результат: его требуется получить заново. Возврат: «Вернуться к слайду» или Escape.

## Связи и выводы темы

Цель задаёт результат работы, поля предоставляют нужные данные, проверки обнаруживают недопустимое значение, а состояния объясняют дальнейший путь. Поэтому успешный макет без офлайн-ожидания и конфликта не задаёт весь сценарий.

Результат: офлайн-запись сохранена; пользователь видит ожидание синхронизации; серверное завершение остаётся отдельным постусловием. Результат: у полей определены смысл и режимы; превышение остатка исправимо; отправка не создаёт ложного подтверждения. Результат: ноль отклоняется на обоих уровнях; подпись можно повторить; сетевой сбой не уничтожает работу. Результат: конфликт имеет отдельный экран и проверяемое восстановление; макет связан с контрактом и критерием приёмки.
